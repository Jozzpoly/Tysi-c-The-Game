# Interaction Anti-Dogma

## Purpose

The Experience Foundation is at risk of replacing weak UI conventions with a new ideology. This document exists to stop that.

Every principle in this research program is conditional. The target is not maximal embodiment, maximal directness, maximal realism or maximal feedback. The target is a justified interaction relationship for the task, user, body, platform and authoritative system.

## 1. Truth is not realism

A digital object can be truthful without behaving like a literal physical object.

Truth means:

- its interaction laws are internally coherent;
- the user can form reliable expectations;
- consequences are causally legible;
- authority is not fabricated;
- important state does not change invisibly.

A card may use magnetic attraction, elastic resistance or non-physical spatial compression if those laws are consistent and useful.

Reject:

> "real cards do X, therefore digital cards should do X."

Prefer:

> "what prior knowledge does physical reality give us, and where is digital behavior better?"

## 2. Direct manipulation is not always best

Direct manipulation is powerful when the domain object and the user's intention align.

It becomes poor when:

- the action is abstract or global;
- repetitive manual work obscures a higher-level intent;
- precision exceeds what the body/input device can provide;
- accessibility requires alternatives;
- the user needs to act on a relation rather than an object;
- a learned instrument expresses intent more directly.

Example:

Dragging ten objects individually to align them is motor-direct but semantically indirect compared with a good alignment instrument.

Therefore distinguish:

- motor directness;
- semantic directness;
- causal directness.

Do not optimize one blindly.

## 3. More physicality is not automatically more embodied

Adding inertia, lag, bounce, tilt, shadow and collision can make an object feel less under control.

Perceived embodiment requires a stable perception-action loop. If the user must constantly decode or correct the interface's decorative dynamics, the object becomes alien rather than bodily/tool-like.

Physicality should increase:

- predictability;
- control confidence;
- material identity;
- expressive range;
- causal comprehension.

If it decreases those qualities, it is probably decoration or simulation vanity.

## 4. Weight must not secretly mean input lag

Slow following can imply mass, but it can also simply feel broken.

Potential contributors to perceived weight include:

- rotational lag around a grab point;
- resistance to acceleration;
- neighbor displacement;
- release follow-through;
- settle time;
- sound;
- contact deformation;
- target response;
- pseudo-haptic control/display manipulation.

Input acknowledgement should remain immediate even when the object has inertia.

## 5. 1:1 mapping is not automatically truthful

On touchscreens, literal co-location creates occlusion and precision problems. A controlled visual offset, proxy, lens or adaptive control/display relationship may better preserve the user's intention.

But decoupling must remain legible.

Research question:

> when does a helpful correction still feel like "my object", and when does it feel like the system is taking over?

## 6. Self-teaching is not rule hiding

Behavioral constraints should reduce the need for repetitive instruction, but arbitrary or strategic rules may still need explicit explanation.

Use the sequence:

`affordance -> exploration -> behavioral response -> local explanation -> deeper help on demand`

Do not force users to reverse-engineer hidden rules from mysterious motion.

## 7. Less chrome is not automatically better

Panels, numbers, labels, histories and diagrams are legitimate when the information is:

- abstract;
- global;
- historical;
- comparative;
- impossible to embody safely;
- needed for expert inspection.

The rule is not "no HUD".

The rule is:

**do not use detached chrome to compensate for a broken causal relationship that could be shown at the source.**

## 8. Animation is not automatically continuity

Animation can preserve object identity and reveal transitions. It can also:

- obscure change;
- delay control;
- attract attention to irrelevant motion;
- create false causality;
- make repeated work exhausting.

Use motion when it helps the user apprehend a real transition.

Avoid motion that grants agency or importance to decoration over semantics.

## 9. Immediate feedback is not the same as immediate outcome

A system should acknowledge contact rapidly.

It should not fabricate authoritative outcomes to appear fast.

Separate:

1. local contact acknowledgement;
2. reversible manipulation;
3. provisional/pending commit state;
4. authoritative acceptance/rejection;
5. consequence;
6. cosmetic tail.

Optimism belongs only where reversal is honest and understandable.

## 10. Streamlining can become paternalism

Game-feel literature identifies support/streamlining as helping execute user intention. This is valuable but dangerous.

The system should not:

- silently choose among materially different intentions;
- auto-sort away user organization;
- auto-correct unusual but valid construction;
- hide constraints by doing the work for the user;
- convert exploratory movement into commitment.

Assistance should preserve agency and make its intervention legible when material.

## 11. User organization is not sacred forever

Spatial organization can be part of cognition, but preservation has costs.

The system may need:

- explicit reset/re-sort;
- import of new objects;
- conflict resolution;
- cross-device adaptation;
- recovery from impossible layouts.

The principle is not "never move user objects".

It is:

**do not destroy user-created structure casually or invisibly.**

## 12. Quiet-life feedback is not idle animation

A living interface is not one in which everything subtly floats forever.

Between actions, life can come from:

- responsive focus;
- latent affordance;
- opponent/state presence;
- persistent traces of consequence;
- environmental responsiveness;
- meaningful anticipation.

Ambient motion without semantic value can make a system feel noisy or cheap.

## 13. Mobile and desktop need shared semantics, not shared mechanics

The same game concept can have different interaction bodies.

Mobile has:

- finger occlusion;
- touch contact area;
- no hover;
- one-handed thumb constraints;
- device motion/haptic possibilities;
- small spatial budget.

Desktop has:

- precision pointing;
- hover/proximity states;
- larger travel distances;
- right-click/modifier/tool possibilities;
- more visible workspace.

Do not force gesture parity.

Preserve semantic parity and causal truth.

## 14. Accessibility can legitimately break embodiment

A highly embodied interaction may be difficult or impossible for some users.

Keyboard navigation, switch control, screen readers, reduced motion and alternative input may require explicit abstractions.

Accessibility is not a degraded fallback. It is an alternative embodiment of the same semantic contract.

## 15. Expertise changes what "intuitive" means

Novices benefit from prior-world knowledge and discoverability. Experts may prefer compact, learned instruments with higher expressive power.

A mature system may therefore support a progression from:

- direct discovery;
- stable learned gestures/instruments;
- expert shortcuts/abstractions.

Do not freeze the entire interface at first-contact simplicity.

## 16. Metrics can mislead

Fast completion does not necessarily mean good interaction.

A slower interaction can be superior if it improves:

- understanding;
- error recovery;
- confidence;
- enjoyment;
- skill expression;
- long-term memory;
- exploratory freedom.

Conversely, "feels good" once may be novelty.

Evaluate repeated use, failure, interruption and learning.

## 17. Donor concepts are not universal laws

A finding should be promoted carefully:

`fixture-specific observation -> Tysiac pattern -> candidate strong concept -> cross-project donor`

The last transition requires successful re-embodiment in a materially different domain.

Do not call preferences laws.

## Review question

Whenever the project begins saying "we always should...", stop and ask:

- Under what task conditions?
- For which user skill level?
- On which platform/body?
- What competing quality are we trading away?
- What evidence supports this?
- What observation would falsify it?
